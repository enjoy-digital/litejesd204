# JESD204C link layer {#link-204c}

This chapter describes the JESD204C link layer: the per-lane logic that scrambles the blocks,
builds the sync word of the sync headers, and locks on blocks and extended multiblocks. Read it
to understand how a JESD204C lane comes up without SYNC~ or ILAS. Blocks, sync words and extended multiblocks are explained in
[JESD204C and 64b/66b](#jesd204c-primer).

## At a glance {#lc-glance}

| Item | Value |
|------------------------|------------------------------------------------------------------|
| Classes | `LiteJESD204CLinkTX`, `LiteJESD204CLinkRX`, one per lane |
| Word | One 66-bit block per link clock: 64-bit payload, 2-bit sync header |
| Octet order | First octet of the lane in the most significant octet of the block |
| Scrambler | 1 + x^39 + x^58, self-synchronous, 64 bits in parallel |
| Sync word | CRC-12 mode: end-of-multiblock, EoEMB, pilots, CRC-12 |
| Multiblock | 32 blocks; E multiblocks per extended multiblock |
| Command channel | Bits sent as 0, not used on receive |
| Lock | Sync header lock (PHY RX domain), then extended multiblock lock |
| Clock domains | `jesd`; the PHY RX domain for the sync header lock |

A JESD204C link has no SYNC~, no CGS and no ILAS. Each lane comes up on its own from the sync
headers, and the LEMC of the core aligns the lanes ([TX and RX cores](#cores)).

## TX datapath {#lc-tx-datapath}

The TX link layer turns each 64-bit lane word into a block and a sync header, as the figure
below shows. The payload goes through the scrambler; the headers spell out one sync word per
multiblock, one bit per block.

![JESD204C TX link layer. Follow the cyan path: the lane word is reordered, scrambled and
registered twice before the crossing; the CRC-12 is computed on the scrambled data and goes
into the sync word, which gives the 2-bit header of each block.](c_tx_datapath.svg)

**Octet order.** The transport layer puts the first octet of a lane in bits 7 to 0. The link
layer reverses the octets so that the first octet sits in the most significant octet of the
block, the order of the scrambler and the CRC. The receiver reverses them back.

**Scrambler.** It scrambles the 64 bits with 1 + x^39 + x^58, most significant bit first, in one
link clock. Its output is combinational; two registers follow it. The descrambler of the
receiver is self-synchronous, so no seed is shared.

**Block counters.** A block counter (0 to 31) and a multiblock counter (0 to E-1) free-run in
the link layer. Each LEMC boundary of the core realigns them on the start of an extended
multiblock and sets `ready`. The link layer is therefore ready from the first LEMC boundary
after `enable`.

**CRC-12.** It is computed over the scrambled payload of each multiblock and restarted at the
start of the next one. The result goes into the sync word of the next multiblock, as the
standard defines it.

**Sync word.** At the start of each multiblock, the sync word generator loads 32 bits: the
CRC-12 of the previous multiblock, the command channel bits (0), the EoEMB bit on the last
multiblock of an extended multiblock, the pilot bits and the end-of-multiblock sequence `00001`.
It sends them most significant bit first, one per block, as the header `01` for a 1 and `10` for
a 0.

The counters and the sync word follow the delayed data, so that bit 31 of each sync word goes
out with block 0 of its multiblock. The datapath latency is two link clocks.

## RX datapath {#lc-rx-datapath}

The RX link layer locks in two steps, as the figure below shows. The block lock finds the block
boundaries in the PHY RX domain and drives the gearbox slip of the PHY. The extended multiblock
lock then finds the sync word in the headers, in the link clock domain.

![JESD204C RX link layer. Follow the cyan path: the block goes through the crossing, the
descrambler and the octet reorder; the header feeds the block lock in the PHY RX domain, which
slips the PHY, and the sync word receiver, which gives the lock; the CRC check takes the scrambled
payload from the crossing.](c_rx_datapath.svg)

**Block lock.** The block lock counts sync headers. A valid header is `01` or `10`; an invalid
one (`00` or `11`) means the gearbox is not on a block boundary. In HUNT, an invalid header
pulses `rx_slip`, then the block lock ignores the headers for 32 PHY RX clocks while the gearbox
applies the slip.

After 64 valid headers in a row it locks, and 16 invalid headers in a row drop the lock
(`BlockSync`).

**Extended multiblock lock.** The sync word receiver shifts in one header bit per block and
looks for the end-of-multiblock sequence. Its state machine has three states (`SyncWordRX`):

- **INIT.** It waits for an EoEMB while the block lock holds.
- **HUNT.** It counts blocks modulo the extended multiblock. An end-of-multiblock missing at a
  multiblock boundary, an EoEMB missing at the extended multiblock boundary, or the loss of
  block lock returns it to INIT. Three more EoEMB at the right spacing move it to LOCK.
- **LOCK.** It sets `ready`. It counts the markers missing at their expected position and
  returns to INIT after 8 of them without a correct EoEMB in between, or on the loss of block
  lock. An extra marker elsewhere is not counted.

**CRC check.** The receiver computes the CRC-12 of each multiblock over the scrambled payload,
as received. It compares it with the CRC carried by the sync word of the next multiblock. The
check starts after three ends of multiblock in LOCK, and each mismatch pulses `crc_error`.

**Data.** The descrambler, a register and the octet reorder give the 64-bit lane word, with one
link clock of latency. The receiver also gives two strobes to the core: `frame_start` with the
first word of each extended multiblock, and `mid_frame` at its middle. The RX core uses them to
start and check the lane deskew ([Lane deskew](#cores-deskew)).

## Thresholds {#lc-thresholds}

The thresholds are parameters of the classes; the cores use the defaults below.

| Threshold | Default | Parameter |
|----------------------------------------|---------|---------------------------|
| Valid headers to lock a block | 64 | Fixed |
| Invalid headers in a row to unlock | 16 | `thresh_sh_err` |
| PHY RX clocks ignored after a slip | 32 | `slip_latency` |
| EoEMB to lock, the first included | 4 | Fixed |
| Missing markers to unlock | 8 | `thresh_emb_err` |
| Ends of multiblock before the CRC check | 3 | Fixed |

The block lock also counts the invalid headers seen in LOCK in a saturating 16-bit counter,
`sh_errors`. No register exposes it.

## PHY interface {#lc-phy}

The link layer exchanges one block per link clock with the PHY: a 64-bit data word and a 2-bit
header, plus the `rx_slip` input of the receive gearbox. [PHYs: LiteICLink
transceivers](#phys-204c) gives the full contract and the availability of such PHYs.

## Limitations {#lc-limitations}

- **Scrambling.** Scrambling is mandatory in JESD204C. The `scrambling` setting of
  `JESD204CSettings` and the `scrambling` argument of the cores turn it off for debugging only;
  the link scrambles when both are true.
- **Command channel.** The command bits of the sync word are sent as 0 and decoded on receive,
  but not used.
- **Modes.** Only the CRC-12 sync word mode is implemented: no FEC, no 64b/80b.
- **Counters.** The invalid sync headers of the block lock are not visible in the registers.

The code issues among these are listed with their workarounds in
[Known issues](#debug-known-issues).

## In the code {#lc-code}

| Class | Role |
|--------------------------------------|------------------------------------------------|
| `Scrambler64b66b`, `Descrambler64b66b` | 1 + x^39 + x^58 scrambling, combinational |
| `CRC12` | CRC-12 over the scrambled payload |
| `SyncWordTX` | Sync word generation, one header bit per block |
| `SyncWordRX` | Extended multiblock lock, CRC and command fields |
| `BlockSync` | Sync header lock and gearbox slip, PHY RX domain |
| `LiteJESD204CLinkTX` | TX counters, datapath and sync word |
| `LiteJESD204CLinkRX` | RX lock, CRC check, datapath and strobes |

All are in `litejesd204/link_204c.py`. The scrambler, the CRC and the sync word follow the
formulation of the open source JESD204 HDL of Analog Devices, for interoperability, as the
header comment of the file states.
