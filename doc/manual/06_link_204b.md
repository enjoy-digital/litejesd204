# JESD204B link layer {#link-204b}

This chapter describes the JESD204B link layer: the per-lane logic that scrambles the data,
inserts the alignment characters, runs CGS and ILAS, and follows SYNC~. Read it to understand
what a lane carries at each phase and why a link does or does not come up. The phases of the
standard are explained in [JESD204 in a nutshell](#jesd204-primer).

## At a glance {#lb-glance}

| Item | Value |
|------------------------|------------------------------------------------------------------|
| Classes | `LiteJESD204BLinkTX`, `LiteJESD204BLinkRX`, one per lane |
| Word | 32 bits, 4 octets per link clock, one K flag per octet |
| Octet order | Octet 0 (bits 7 to 0) first on the line |
| Scrambler | 1 + x^14 + x^15, self-synchronous, seed `0x7f80` |
| Frame sizes | 1, 2 or 4 octets per frame (whole frames per word) |
| Phases | CGS, ILAS, data |
| ILAS | 4 multiframes, configuration octets in the second |
| SYNC~ | Re-synchronization after 4 link clocks low; no error reports |
| RX alignment | From the position of /R/; held from the start of ILAS |
| Clock domain | `jesd` |

## Lane word {#lb-word}

The link layer moves one 32-bit word per link clock and per lane: 4 octets, octet 0 in bits 7 to
0 and first on the line. Each octet has a K flag (`ctrl`) that marks a control character, encoded
by the PHY as a K code group. Two internal flags per octet mark the last octet of a frame and of
a multiframe.

## TX datapath {#lb-tx-datapath}

The TX link layer takes the lane word from the transport layer and sends one of three sources to
the PHY: the CGS pattern, the ILAS, or the data. The figure below shows the data path and the
selection.

![JESD204B TX link layer. Follow the cyan path: the lane word goes through the scrambler, the
framer and the alignment character inserter; the output selector sends CGS, ILAS or data to the
crossing, as the state machine decides.](b_tx_datapath.svg)

**Scrambler.** It scrambles the 32 bits of the word with the polynomial 1 + x^14 + x^15, in the
order of the octets on the line, and adds one link clock of latency. Its state starts at
`0x7f80`. The self-synchronous descrambler needs no common seed. The `scrambling` argument of
the core turns it off (`enable`).

**Framer.** It marks the last octet of each frame and of each multiframe, from K and
`octets_per_frame`, the octets of one converter in a frame. It requires whole frames in a word:
a frame has 1, 2 or 4 octets, and K is a multiple of the frames per word. Its multiframe counter
starts with the data phase; the `framing` setting turns the marks off.

**Alignment character inserter.** It replaces some data octets with alignment characters, so
that the receiver could monitor the frame and multiframe positions. The rules depend on
scrambling:

| Scrambling | Last octet of a multiframe | Last octet of a frame |
|------------|---------------------------------|---------------------------------|
| On | `0x7C` sent as /A/ (K28.3) | `0xFC` sent as /F/ (K28.7) |
| Off | Same as before: sent as /A/ | Same as before: sent as /F/ |

Without scrambling, the inserter compares each octet with the octet at the same position one
link clock earlier. That is the previous frame only with 4-octet frames; the standard compares
with the previous frame. The replacer of the receiver has a second problem, described with it
below: the unscrambled mode is not usable, so keep scrambling on, the default.

The datapath latency is one link clock, from the scrambler.

## Code group synchronization {#lb-cgs}

During CGS, the TX link layer sends /K/ (K28.5) on all four octets of every word. The PHY of the
receiver finds the comma in the bit stream and aligns its symbols on it. The RX checker declares
the CGS valid when one word holds four /K/ characters with their K flags, sampled at an LMFC
boundary: with no LMFC boundary, the receiver never releases SYNC~ and no ILAS starts.

## Initial lane alignment sequence {#lb-ilas}

The ILAS lasts four multiframes of F x K octets, F being `octets_per_lane`. Each multiframe
starts with /R/ (K28.0) and ends with /A/ (K28.3). The second multiframe carries /Q/ (K28.4) in
its second octet, then the 14 configuration octets.

The other octets are a counter that wraps at 256, its value being the position of the octet in
the sequence.

The configuration octets come from the settings: the parameters minus one, as the standard
encodes them, the scrambling bit, the device and bank identifiers, the subclass (1), the version
(JESD204B) and a checksum. The lane identifier is the position of the lane in the PHY list. A
script can print the fields ([Getting started](#getting-started)).

Both the generator and the checker hold the whole sequence in a lookup table, built at
elaboration time. The `with_counter` parameter of the ILAS classes replaces the counter with
zeros; the cores keep the counter.

## RX datapath {#lb-rx-datapath}

The RX link layer first aligns the octets, then feeds three consumers: the CGS checker, the ILAS
checker and the data path, as the figure below shows. The data path undoes what the transmitter
did, in reverse order.

![JESD204B RX link layer. Follow the cyan path: the word from the crossing goes through the
aligner, then the alignment character replacer, the deframer and the descrambler; the CGS and
ILAS checkers watch the aligned word.](b_rx_datapath.svg)

**Alignment character replacer.** With scrambling, it only clears the K flags of /A/ and /F/:
their octet values are the data. Without scrambling, it puts back the octet received at the same
position one link clock earlier, even when that octet was itself a replaced character. Two
consecutive replaced frames are not restored, even from a TX core of this project
([Known issues](#debug-known-issues)).

**Deframer.** It passes the data through. It does not check the frame or multiframe positions.

**Descrambler.** It reverses the scrambler, with one link clock of latency. Being
self-synchronous, it recovers after the first word whatever its starting state.

## Byte alignment {#lb-aligner}

The PHY aligns symbols, but it can deliver the first octet of a frame in any of the four octets
of the 32-bit word. The aligner finds the /R/ that starts each ILAS multiframe and shifts the
words so that /R/ lands in octet 0, as the figure below shows (`Aligner`). It adds one link clock
of latency.

![Byte alignment. Look at the /R/ character: it arrives in octet 2 of a word; the aligner takes
octets 2 and 3 of that word and octets 0 and 1 of the next to build an output word that starts
with /R/.](b_aligner.svg)

The aligner updates its position on each /R/ until the ILAS starts, then holds it (`hold`) until
the link layer returns to CGS. A data octet decoded as K28.0 by mistake can no longer rotate the
lane. The aligner reports such a hit with a `realign` pulse anyway and gives its position on
`alignment`; the RX core keeps both per lane for the registers.

## State machines {#lb-fsm}

Each link layer has a state machine that follows the phases of the standard, as the figure below
shows. The TX one waits for SYNC~ to be released; the RX one drives SYNC~.

![JESD204B state machines. Follow the TX machine on the left from CGS to ILAS to data, and the RX
machine on the right from CGS to ILAS to data; SYNC~ is asserted by the RX machine in RECEIVE-CGS
and released from ASSERT-SYNC onward.](b_fsm.svg)

**TX.** SEND-CGS sends /K/ and holds the ILAS generator, the scrambler and the framer in reset.
It moves to SEND-ILAS at the first LMFC boundary with SYNC~ released. SEND-ILAS plays the
sequence and moves to SEND-DATA on its last word. SEND-DATA sends the data path and sets `ready`.

**TX and SYNC~.** In SEND-DATA, the TX link layer returns to SEND-CGS when SYNC~ stays asserted
for 4 consecutive link clocks (`WaitTimer(4)`). A shorter pulse is ignored: the standard uses
short pulses to report errors, which the core does not act on.

**RX.** RECEIVE-CGS asserts SYNC~ and drives the `align` output, which the RX core connects to
the PHY so that it searches for the comma. At the first LMFC boundary with a valid CGS word, it
moves to ASSERT-SYNC.

ASSERT-SYNC releases SYNC~ and waits for an /R/ in octet 0 with no other K flag. RECEIVE-ILAS
checks the sequence; RECEIVE-DATA sets `ready`.

**RX checks.** In RECEIVE-ILAS, every word is compared with the lookup table: control
characters, configuration octets and counter. A difference sends the link layer back to
RECEIVE-CGS while `ilas_check` is set. In RECEIVE-DATA, a word of four /K/ characters, the
transmitter restarting its CGS, also sends it back.

Because the ILAS check compares the configuration octets, the converter must advertise exactly the
parameters, identifiers and lane numbers of the settings. A converter whose ILAS filler is not
the counter fails the check too. The `ilas_check_disable` field of the `control` register turns
the check off ([TX and RX cores](#cores-control)).

The RX core releases SYNC~ only when every lane has released it: the core output is the AND of
the lanes. The TX core gives the same SYNC~ input to all its lanes.

## Limitations {#lb-limitations}

- **Error reporting.** The RX link layer never reports errors on SYNC~, and the TX link layer
  ignores short SYNC~ pulses.
- **Monitoring.** The receiver does not check the /A/ and /F/ positions, does not count
  disparity or not-in-table errors, and has no frame or lane alignment monitoring after the ILAS.
- **Frame sizes.** The framer accepts F of 1, 2 or 4 octets only.
- **Unscrambled mode.** Not usable: the alignment characters are compared with the octet one link
  clock earlier instead of the previous frame, and two consecutive replacements are not restored
  on receive. Keep scrambling on.
- **Sizing when M and L differ.** The framer is sized with `octets_per_frame` and the ILAS with
  `octets_per_lane`; when M and L differ, the two disagree.
- **Two scrambling knobs.** The `scrambling` argument of the core drives the scrambler, while the
  scrambling bit of the configuration octets comes from the settings. Set both the same way.

Each of these is listed with its workaround in [Known issues](#debug-known-issues).

## In the code {#lb-code}

| Class | Role |
|------------------------------|-------------------------------------------------------|
| `Scrambler`, `Descrambler` | 1 + x^14 + x^15 scrambling, latency 1 |
| `Framer`, `Deframer` | Frame and multiframe marks; pass-through on RX |
| `AlignInserter` | /A/ and /F/ insertion |
| `AlignReplacer` | /A/ and /F/ replacement |
| `Aligner` | Octet alignment on /R/, `hold`, `alignment`, `realign` |
| `CGSGenerator`, `CGSChecker` | /K/ pattern and its check |
| `ILASGenerator`, `ILASChecker` | Lookup table of the ILAS and its comparison |
| `LiteJESD204BLinkTX` | TX state machine and datapath |
| `LiteJESD204BLinkRX` | RX state machine, aligner and datapath |

All are in `litejesd204/link.py`; the control characters and configuration fields are in
`litejesd204/common.py`.
